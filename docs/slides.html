Commit Gemfile and Gemfile.lock, like package.json and its lockfile.

Heroku's Ruby buildpack runs bundle install.

A dependency list is only part of what makes an app runnable.

About 60 seconds. This is an addition to an existing Gemfile. Bundler installs Ruby libraries using the lockfile; a native extension may need compatible binaries or build tools. 3 / 7 · Make the hidden work visible

On a bare server, those jobs become yours

  1. Get the code. Connect over SSH and clone the repo.
  2. Install the environment. Runtime, libraries, and database connection.
  3. Start the app. For example, Node or Puma on port 3000.
  4. Route web requests. Nginx or Apache in front, handling HTTPS.
  5. Keep it running. Restart after a crash or reboot.
  6. Give it a name. Point DNS at the endpoint.

About 60 seconds. A platform was doing these jobs for us. On a fresh Linux server we have to account for each one. For JavaScript, picture an Express or Fastify process behind Nginx, kept alive by systemd or PM2. We will return to DNS after the four app examples. The immediate problem is repeating these steps for the next release.

4 / 7 · Repeatable commands

A script writes down the steps

#!/usr/bin/env bash
set -euo pipefail
ssh deploy@myapp.com <<'EOF'
  cd /var/www/myapp
  git pull origin main
  BUNDLE_DEPLOYMENT=1 bundle install   # or npm ci
  bundle exec rake db:migrate        # or npm run migrate
  sudo systemctl restart myapp
EOF

Now someone else can deploy. But a failed install can leave the live directory half-updated.

About 60 seconds. This is a useful first improvement, and it may be enough for a small app. The important limitation is that it edits the running release in place. If installation fails after git pull, old processes can be running against new files. We want to prepare the replacement somewhere else and switch only when it is ready. BUNDLE_DEPLOYMENT=1 also works with Bundler 4, unlike the removed bundle install --deployment flag.

5 / 7 · Capistrano

Prepare a release before switching to it

About 75 seconds. Capistrano prepares a timestamped release directory, links shared files, and runs the build before switching current. The previous directory stays available for rollback. The symlink switch is atomic; that does not make the entire deployment or a database migration atomic. Capistrano still expects the runtime and system libraries to be installed on the host. The same release-directory pattern works for a Node application with different build and restart commands.

Docker packages the environment; Kamal ships it

Build an image containing the app, runtime, and dependencies.

Push the versioned image to a registry.

Kamal starts the new container and switches traffic after its health check passes.

The release is prepared before the switch. The host still needs Docker and configuration.

About 75 seconds. Docker moves application environment setup into the image. Kamal coordinates running a new version and switching traffic to it with kamal-proxy. Keep data and secrets outside the image. This does not undo database migrations, patch the host, or create the surrounding network and database. Capistrano remains a reasonable option; keep the trade-off discussion brief here.

Stack 1 Structure

A private bucket behind a CDN

To serve a static site we need somewhere to keep the files, an HTTPS endpoint through a CDN, and permissions that let the CDN read the files while keeping the bucket private.

Let's describe that setup in Terraform, then upload the site separately. Terraform provisions the hosting infrastructure; uploading the built files deploys the site.

Walk the request left to right. The part people skip is the bottom arrow: nobody can read the bucket directly, not even with a website endpoint.

Origin access control replaced origin access identity in 2022. Tutorials still show OAI, and it still works, which is how old patterns survive.

This is the standard AWS CLI. The explicit --endpoint-url sends both commands to Floci on the laptop. Use the demo's test credentials and us-east-1 region.

These commands create a bucket and upload a file. They do not configure website access or a CDN. Then run stack 1 to build the complete hosting setup from the diagram.

A line to say: "Could I just point a domain at this bucket? Almost: turn on website hosting, make it public, name the bucket after the domain, and add a DNS record. But you'd get HTTP only. HTTPS on your own domain needs a CDN in front, which is why stack 1 has one."

What that takes on real AWS (checked against AWS's docs, 2026-10-12):

1. Turn on static website hosting with index.html as the index document. That gives the bucket a separate website endpoint, http://BUCKET.s3-website-us-east-1.amazonaws.com. The normal S3 endpoint does not serve an index document: a request to the bucket root returns a list of object keys, and errors come back as XML, not HTML.

2. Make it public, which is two steps: turn off Block Public Access (on the bucket, and on the account if it is on there), then add a bucket policy allowing s3:GetObject to "*". The website endpoint only serves publicly readable content. Since April 2023, buckets created through the CLI, SDKs, APIs or CloudFormation get Block Public Access on and ACLs disabled by default; console-made buckets already did. It applies to new buckets only.

3. Name the bucket exactly after the hostname, such as www.example.com. AWS says the bucket names must match the domain name exactly. Bucket names are global, so if someone else owns that name, you cannot use it.

4. Point DNS at the website endpoint: a CNAME for www, and for the bare domain a Route 53 alias record, which is what AWS's tutorial uses. (A CNAME is not allowed at the bare domain; that is a DNS rule, stated from memory, not from AWS's docs.)

Then it is HTTP only. AWS: "Amazon S3 website endpoints do not support HTTPS." For HTTPS AWS points to CloudFront or Amplify Hosting. Some domains will not load over HTTP at all: .dev and .app are on browsers' HSTS preload list, so browsers force HTTPS for them.

The two approaches are alternatives, not layers. CloudFront's docs say a bucket set up as a website endpoint cannot use origin access control: CloudFront has to treat it as an ordinary custom origin, which means the bucket stays public. So it is either a public website bucket, HTTP only unless a CDN is in front, or what stack 1 builds: a private bucket that only its CloudFront distribution can read. (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html)

Keep this about real AWS. Whether Floci emulates S3 website endpoints is untested, and Floci does not enforce bucket privacy by default, so a demo there would make public look like it does not matter.

Sources: https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteEndpoints.html ; https://docs.aws.amazon.com/AmazonS3/latest/userguide/website-hosting-custom-domain-walkthrough.html ; https://aws.amazon.com/about-aws/whats-new/2023/04/amazon-s3-security-best-practices-buckets-default ; https://en.wikipedia.org/wiki/.dev

Stack 1 The code that matters

One line of trust

resource "aws_s3_bucket_policy" "site" {
bucket = aws_s3_bucket.site.id
policy = jsonencode({
  Statement = [{
    Effect    = "Allow"
    Principal = { Service = "cloudfront.amazonaws.com" }
    Action    = "s3:GetObject"
    Resource  = "${aws_s3_bucket.site.arn}/*"
    Condition = {
      StringEquals = {
        "AWS:SourceArn" = aws_cloudfront_distribution.site.arn
      }
    }
  }]
})
}

Why it matters

"CloudFront may read" would let any distribution in any account read your bucket. The condition narrows it to this one.

No ID is typed. Terraform wires the distribution's ARN in, so the policy can't point at last month's CDN.

The highlighted line is the difference between "private" and "private unless someone else also uses CloudFront".

Everything is a reference, not a pasted ID, which is the same rule that fixes the Act III bug later.

Why the condition matters, from AWS's docs (checked 2026-10-12): a policy that trusts a service principal such as cloudfront.amazonaws.com "is only authorizing the AWS service principal, and not the actor who configured the calling service". Without the condition, a distribution someone else set up could use CloudFront's trust to read your bucket. AWS calls this the confused deputy problem and recommends aws:SourceArn (or aws:SourceAccount) wherever a service principal is granted access. CloudFront's own guide says to use the condition so CloudFront can read the bucket "only when the request is on behalf of the CloudFront distribution".

Say this about Floci: it stores this policy but does not enforce it unless its enforcement settings are on (FLOCI_SERVICES_S3_ENFORCE_AUTH and FLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED, both off by default). Delete the resource and the demo site still works; an anonymous read of the bucket returns 200. On real AWS, delete it and the site returns 403. One sentence is enough: "Floci keeps this but does not check it; AWS does."

Sources: https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html ; https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html ; docs/FINDINGS.md for the Floci behavior.

Stack 2 The code that matters

"Public" still needs two permissions

resource "aws_lambda_function_url" "api" {
function_name      = aws_lambda_function.api.function_name
authorization_type = "NONE"
}

resource "aws_lambda_permission" "url" {
action                 = "lambda:InvokeFunctionUrl"
principal              = "*"
function_url_auth_type = "NONE"
}

resource "aws_lambda_permission" "invoke_via_url" {
action                   = "lambda:InvokeFunction"
principal                = "*"
invoked_via_function_url = true
}

Since October 2025

New function URLs need both statements, even with auth NONE. Miss the second and callers get 403 Forbidden.

The console and SAM add both for you. Terraform, the CLI and CloudFormation don't, so anything copied from an older tutorial is missing one.

docs.aws.amazon.com/lambda/latest/dg/urls-auth.html

This is the October 2025 trap. Works in the console, 403 from Terraform, and the difference is one boolean.

Floci accepts either version, so the emulator won't catch it for you.

Stack 3 Structure

Most of it is the fence

RDS insists on two subnets in two availability zones, even for a single instance. That surprises people every time.

The database security group admits Postgres from the app's security group, a reference not an IP range. Same rule as the Act III fix: refer to the thing, never copy its address.

The app host is in the Terraform as it would be on real AWS: an aws_instance in the public subnet, behind the app security group, which admits 80 and 443 from anywhere and 22 (Kamal's SSH) from one address. Floci creates the instance too, as an Ubuntu container. On the laptop Kamal still deploys to a stand-in container with sshd and Docker, because Docker inside Floci's instance needs extra steps that are not wired up yet.

Floci does not enforce security groups by default, so on the laptop the fence is described, not tested. On real AWS it is what keeps Postgres private.

Compare stack 2, which had no fence at all: nine resources and not one of them network.

Stack 3 The code that matters

Public is a route, not a setting

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

Three ideas

A route makes it public. The public subnet sends everything else to the internet gateway. The private ones have no such route.

A security group makes it allowed. Postgres admits 5432 only from the app's group, by reference, not by address.

Two zones, because RDS asks. One database still needs subnets in two availability zones.

The line to say: public versus private is three resources, a gateway, a route and an association. Delete the route and the public subnet becomes private. There is no "public" checkbox on a subnet; map_public_ip_on_launch only hands out public addresses, it is the route that makes them reachable.

Addresses, in one sentence: the VPC is 10.20.0.0/16, about 65,000 private addresses that are yours. Each subnet is a /24 slice of it, 256 addresses, of which AWS keeps 5. cidrsubnet() carves the slices so nobody types them: public 10.20.1.0/24, private 10.20.10.0/24 and 10.20.11.0/24.

Availability zones: a subnet lives in one zone, roughly one data center. RDS wants a subnet group across at least two zones even for one instance, which is why there are two private subnets.

Routes and security groups answer different questions. A route decides whether traffic can get somewhere; a security group decides whether it is allowed in once it arrives. Security groups are stateful: allow the request in and the reply goes back out on its own.

If the route points at a gateway that is detached or deleted, the route stays but its state becomes blackhole, and matching traffic is dropped (EC2 API reference, Route: blackhole means the target is not available, for example a detached gateway). Nothing answers, so connections hang and time out. With the route and gateway but no public IP, an instance still cannot get out: the internet gateway only translates for instances with a public address, which is why the public subnet sets map_public_ip_on_launch.

A diagnostic worth giving the room: if a connection hangs and then times out, packets are being dropped, so look at routes and security groups, which both drop silently. If it says "connection refused" straight away, you reached the machine and nothing is listening on that port, so look at the app. On Floci neither shows, because routes and security groups are not enforced.

The database has three independent layers: private subnets with no route out, publicly_accessible = false, and a security group that only admits the app. Any one of them keeps it off the internet.

What is deliberately missing: a NAT gateway. Private subnets have no outbound internet, and the database needs none. An app in a private subnet would need one to reach the internet, and NAT gateways bill by the hour. Small setups often keep the app in the public subnet behind a security group instead, as this stack does.

If someone asks why the app is public: "Here the app is public behind a security group, which is fine for one server. At work you'll usually see it private, behind a load balancer, with a NAT gateway so it can still reach out." The load balancer becomes the only public thing, which shrinks what can be attacked and spreads traffic across servers. The NAT gateway lets private servers pull images and call APIs without being reachable. This stack skips both because it is one server, and both add resources and monthly cost.

On Floci all of this is stored but not enforced by default, so the network is described here, not tested. The ledger notes have describe-subnets and describe-route-tables commands that show it exists.
